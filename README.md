# sre-capacity-and-readiness

A capacity plan and a readiness review for a small service about to launch: a stepped open-loop load test that finds the knee of one instance and names the resource that saturated, a safe load held for a soak, a six-month fleet plan with headroom for a lost zone that is checked by running the fleet with a zone stopped, the next bottleneck (a shared connection pool) found by scaling out, and a review that gives every checklist item a verdict, an owner and evidence, and ends in one decision.

## Prerequisites

| Tool | Version | Used for |
| --- | --- | --- |
| Docker with Compose v2 | 24 or newer (tested with 24.0.6); give Docker Desktop at least 8 CPUs and 6 GB | the fleet, the load generator, `promtool` |
| Python | 3.12 or 3.13 (tested with 3.13; the CI uses 3.12) | the experiments, the review and the tests |
| GNU Make | 3.81 or newer (the one on macOS works) | every command below |
| Images | `envoyproxy/envoy:v1.32.3`, `postgres:18`, `prom/prometheus:v3.5.0`, and the Python image built from `Dockerfile` | pulled or built on first `make up` |
| Python packages | `aiohttp`, `prometheus-client`, `PyYAML`, `psycopg[binary]`, `psycopg-pool` at run time; pytest, pytest-asyncio, pytest-cov, ruff, mypy, import-linter, pip-audit for development. All pinned with hashes in `requirements.lock` and `requirements-dev.lock`; `make` installs them into `.venv/` | everything |

No cloud account and no secrets (every credential in `docker-compose.yml` and `.env.example` is a local development placeholder). Ports 47280 (edge), 47281 (Envoy admin), 47282 and 47283 (instance a1), 47284 (ledger ops), 47290 (Prometheus) and 47232 (PostgreSQL) must be free; they are published on 127.0.0.1 only and can be changed in `.env`.

The experiments need CPU that is really free: the full fleet at the projected peak is about 5 cores of instances plus the load balancer, ledger, database and load generator. On a busy machine the numbers will be worse and the generator will say so (see "The load generator checks itself" below).

## Setup, run, test, stop

```bash
make up              # builds and starts 8 instances in 3 zones, Envoy, the ledger, PostgreSQL and Prometheus
make run             # the whole exercise in the lesson's order (about 15 minutes), ending in the launch decision
make knee            # step the load up on one instance until p99 climbs; names the saturated resource
make soak            # hold one instance at the safe load for SOAK_SECONDS (default 120; the lesson's real run is 1800)
make plan            # size the fleet from the measured safe load: the formula, the inputs, the result
make zone-loss       # stop the largest zone and run the projected peak on the survivors
make pool-sweep      # reintroduce the shared ledger and step its connection pool up until the SLO holds
make rollout-test    # roll every instance to v2 and back to v1 under load, one at a time
make dependency-test # freeze the ledger and check requests fail fast
make restore-test    # back up the ledger, restore into a scratch database, compare row for row
make review          # the readiness review: every item PASS, FAIL or ACCEPTED RISK, then the decision
make lint            # ruff, format check, mypy, import rules, generated rules in sync
make test            # unit and integration tests with coverage, then promtool
make test-measurements # the committed measurements against the plan, the alerts and the lesson's Done when lines (after make run)
make test-e2e        # smoke tests of the running fleet (needs make up)
make audit           # known-vulnerability check of the locked dependencies
make down            # stops everything and deletes its data
```

`make help` lists every target. Each experiment prints what it measured and writes it to `docs/evidence/<name>.json`; `make test-measurements` holds those committed measurements to the lesson's Done when lines, so a change to the code or the plan that the evidence no longer supports fails the build. Step and soak lengths come from `STEP_SECONDS` (default 10; the lesson's real value is 120) and `SOAK_SECONDS` (default 120; 1800); `CHECK_SECONDS` (default 40) is the length of each fleet run.

What `make run` printed (abridged; the measured numbers vary a little between runs and machines, which is why the plan is built from them and never from the lesson's):

**Status of the measurements.** Everything below the load-dependent experiments is verified; the load-dependent evidence is not committed yet. The two experiments that do not depend on how fast the machine is were run and their evidence is committed:

```text
dependency: 120 requests with the ledger frozen, 120 failed fast (slowest 503 693 ms, bound 750 ms), instance still healthy
restore:    28,467 rows backed up (332,518 bytes, 2.0 s), restored into a scratch database (1.5 s), checksum matched, RTO target 300 s
```

The knee, soak, plan, fleet and pool-sweep experiments need roughly four free cores for about 20 minutes. The machine this repository was built on was running dozens of other containers at a load average above 200 during the whole build window (open-loop generator lag of up to 145 seconds, soak p99 of 6 seconds at 300 requests a second), so every attempt produced numbers that described the machine, not the service, and none was committed. `docs/capacity-plan.md` and `docs/launch-decision.md` are generated from that evidence and are therefore not in the repository either: `make run` writes them. Until it has been run, `make review` reports exactly that (restore verified, the load evidence missing) rather than a launch decision (today it says DON'T LAUNCH YET: rollout and capacity have no evidence, backup and restore pass), and `make test-measurements` fails with a missing-evidence message until `make run` has been run; it is not part of `make test`.

**Verification run of 2026-11-02 (shared machine, load average 9 to 30 from other work).** `make up` built and started the stack (12 containers healthy). `make test` passed (173 tests) and the promtool replays passed. `make test-e2e` passed 4 of 5; the failing one, `test_the_load_balancer_sees_eight_healthy_instances`, saw 15 healthy members. Two attempts at `make run` reached the soak and stopped there:

```text
knee:  500 rps (p99 4.4 ms -> 17.6 ms), CPU of the one core only 49.5% at the knee, so the resource is reported as unknown, not CPU
soak:  375 rps for 120 s, 0 errors, but window p99 up to 174 ms (and 884 ms in the first attempt): not within the 50 ms SLO
plan:  ceil(2000 / 375) = 6 for the peak, 9 in all, but docker-compose.yml defines 8, so `make plan` stops and asks for more instances
```

These numbers describe a loaded Docker VM, not the service: the instance never used a full core before latency rose, and the generator's other steps were noisy. They were not committed (`docs/evidence` holds only the dependency and restore evidence), and `docs/capacity-plan.md` and `docs/launch-decision.md` are still not generated. An earlier attempt got past the full-fleet run and failed in `make zone-loss`: after the instances were recreated, Envoy kept the removed addresses as members while they still passed health checks (`pending_dynamic_removal` in <http://localhost:47281/clusters>), so `cluster.app.membership_healthy` read 13 for 8 instances and `wait_for_members` timed out. That also inflates the fleet alerts. Setting `ignore_health_on_host_removal: true` on the `app` cluster in `deploy/envoy.yaml` is the likely fix, but it could not be confirmed here (Envoy's health checks timed out under the load), so it is not applied.

Pending capacity: on a quiet machine run `make down && make run`, then `make test`, `make test-e2e` and `make test-measurements`; confirm the member count after `make reset-fleet` first and apply the Envoy change if it reads above 8.

## Done when: the lesson's checklist and the proof for each line

| # | Done when (from the lesson) | Command | What proves it |
| --- | --- | --- | --- |
| 1 | A chart shows where p99 rises sharply, and you name the resource that saturated first. | `make knee`; [docs/capacity-plan.md](docs/capacity-plan.md#1-the-knee-of-one-instance) | Not yet measured here (see the status above). `make knee` writes `docs/evidence/knee.json`; the chart is the table in `docs/capacity-plan.md`; `tests/measurements` asserts a knee is found and a resource is named. |
| 2 | A second test at that load for 30 minutes keeps p99 within the SLO the whole time. | `make soak` | Not yet measured here. `make soak` writes `docs/evidence/soak.json`, and `tests/measurements` asserts every window stayed within the SLO. The soak is 120 s by default (the lesson's 30 minutes with `SOAK_SECONDS=1800`). |
| 3 | The plan shows the formula, the inputs and the result, and you check it by running the computed fleet at peak with one-third removed. | `make plan`, `make zone-loss` | Formula and arithmetic: [tests/unit/test_plan.py](tests/unit/test_plan.py) (runs in `make test`). The run against the computed fleet with a zone removed: `make full-fleet`, `make zone-loss` (not yet measured here). |
| 4 | You find what saturates next, and the plan names it with a number. | `make pool-sweep` | Not yet measured here. `make pool-sweep` steps the shared pool until the SLO holds; `make plan-doc` writes the naive and adopted sizes into `docs/capacity-plan.md` and the pool runbook. |
| 5 | Each item is marked pass, fail or accepted risk with an owner, and a restore from backup has actually been tested. | `make restore-test`, `make review` | Restore: **proved**, `docs/evidence/restore.json` (rows and checksum match). Review: `make review` marks every item PASS, FAIL or ACCEPTED RISK with owner, date and evidence ([readiness/checklist.yaml](readiness/checklist.yaml)); the accepted risks are listed there. Items that need load evidence stay FAIL until `make run` has produced it. |
| 6 | The decision fits on one page and every blocker has an owner and a date. | [docs/launch-decision.md](docs/launch-decision.md) | `make review --write` generates it (one page, blockers with owner and date). Not yet generated here, because it must not claim LAUNCH on evidence that has not been measured. |

The chart: the table in [docs/capacity-plan.md](docs/capacity-plan.md) is the chart in text (target rate, achieved rate, p50, p99, errors and the CPU of the instance's one core at each step); `dashboards/fleet.json` imports into Grafana and plots the same series live from Prometheus.

The same checks run as automated tests: [tests/unit](tests/unit) (the knee search, the plan formula, the open-loop test logic, the review, the report, and `test_evidence.py` which holds the committed measurements to each Done when line), [tests/integration](tests/integration) (the instance, a stand-in ledger and the generator over real sockets), [slo/tests](slo/tests) (`promtool` replays of the SLO burn alerts on the Envoy edge and of the fleet-capacity alert) and [tests/e2e](tests/e2e) (smoke tests of the running fleet).

## The load generator checks itself

A load test is only as honest as its generator. `capacity-loadtest` is open-loop: request *i* is scheduled at `start + i / rps` whether or not earlier requests returned, and its latency runs from the *scheduled* arrival to the end of the response ([ADR 0001](docs/adr/0001-open-loop-load-measured-from-the-scheduled-arrival.md)). It also reports its own lag (how late it was, at p99) and prints a warning when that exceeds 5 ms, because then the generator, not the service, is in the number. Past the knee a closed-loop generator would simply send less; this one keeps sending and the queue shows.

## Stretch goals

| Stretch (from the lesson) | Built? |
| --- | --- |
| Repeat the knee test with a larger instance size and decide whether to scale up or out. | No. `cpus` in `docker-compose.yml` is the knob; a Python event loop uses one core, so more than 1.0 CPU would not raise an instance's capacity, which is itself the answer for this runtime. |
| Add autoscaling and test how fast it reacts to a step from half to full peak. | No, and recorded as an accepted risk in the review (`readiness/checklist.yaml`) with the condition that reopens it. |
| Model cost per thousand requests at the planned size and at twice the size. | No. The plan gives instances (and the pool); multiply by the price of one instance. |

## What is simplified for teaching

Only what the lesson scopes out, plus where this build differs from the lesson's text:

- The three "zones" are labels on containers of one Docker host, so the zone-loss test models the capacity effect of a zone failure but not a shared network or power failure. This is recorded as an accepted risk in the review.
- The default request cost is 3,000 rounds of SHA-256 (about a millisecond), half the lesson's, so that the projected-peak fleet test fits on a laptop ([ADR 0003](docs/adr/0003-one-core-per-instance-and-cpu-work-on-the-event-loop.md)). `WORK_ROUNDS=6000` restores the lesson's; all plan numbers come from measuring.
- Steps last 10 seconds and the soak 120, not 2 minutes and 30 minutes. Set `STEP_SECONDS=120 SOAK_SECONDS=1800` for the real thing.
- The shared dependency is a small ledger service with a bounded pool of real PostgreSQL connections; `HOLD_MS=10` makes each request hold its connection for 10 ms, the lesson's average hold time.
- The dashboard is a Grafana-format JSON in the repository, not a Grafana container; the review checks that every query uses a metric the system exports, and the end-to-end test checks that those metrics really are exported.
- Envoy is a single container; it is the one single point of failure in this build.
- "On-call ownership" is a document with roles, not a pager integration.

The dependency rule (domain depends on nothing; application on domain; infrastructure and interfaces on both; nothing on interfaces) is enforced by `make lint` through import-linter. ## Troubleshooting

- **Ports in use:** stop whatever uses them, or set other ports in `.env` (see `.env.example`).
- **The knee test says no knee:** the load never got high enough; raise `--steps` (the default goes to 1,600 requests a second per instance) or raise `WORK_ROUNDS` so that one instance saturates sooner.
- **The generator warns it was late:** the machine is short of CPU. Close other work, give Docker more CPUs, or lower the target; do not trust numbers measured while it warns.
- **`make zone-loss` hangs waiting for healthy instances:** `docker compose ps` should show the survivors healthy; Envoy's view is at <http://localhost:47281/clusters>. If `cluster.app.membership_healthy` counts more instances than exist, look for `pending_dynamic_removal` hosts there (see the verification note above).
- **Logs:** `docker compose logs lb app-a1 ledger`.
